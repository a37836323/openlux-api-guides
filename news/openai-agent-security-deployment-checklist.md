# OpenAI 高风险 Agent 安全措施：上线前检查沙箱、隔离与审计

## 先给结论：先按风险划边界，再决定是否上线

如果你的 Agent 能够调用文件系统、执行代码、访问网络、读取内部数据或修改业务状态，应该在上线前完成四类检查：**执行环境隔离、网络与权限控制、活动审计、模拟攻击验证**。其中，模型生成代码和其他不可信代码应放入更强隔离的沙箱；高风险工作负载应默认与互联网及内部网络隔离。

这篇文章适合负责 AI API、工具调用、Agent 平台、应用安全或上线审核的读者。文章依据 OpenAI 于 2026 年 8 月 18 日公布的高能力模型和带工具工作负载安全措施，结合工程实践整理检查项。需要明确的是，官方材料描述的是 OpenAI 自身研究环境和高风险工作负载，**不是对所有普通 API 应用发布的统一强制规范**。下文的检查清单属于作者建议。

## 官方发布了哪些安全方向

**官方发布事实：**

- OpenAI 将防护分为监控、对齐与安全控制三层。
- 模型生成代码或其他不可信代码，应使用更强沙箱。
- 高风险工作负载应与互联网及内部网络隔离。
- 应移除易受攻击的共享服务，减少常驻权限，并强化安全边界和日志。
- 应持续使用模拟攻击验证安全边界。
- 应监控工具动作、可用的推理信息以及完整活动序列，用于识别未授权访问、数据窃取、破坏行为和绕过防护。

这些内容提供的是安全设计方向，而不是一组可以直接复制到所有 API 应用的固定参数。官方材料没有在给定信息中规定具体沙箱产品、网络拓扑、日志保留周期、告警阈值或模型参数，因此工程团队不应自行把这些缺失内容包装成 OpenAI 的要求。

## 沙箱、网络隔离与最小权限如何落地

### 1. 把代码执行当作高风险边界

模型输出的代码即使看起来只是数据处理，也可能访问文件、调用命令或尝试连接外部服务。因此，代码执行工具不应直接共享宿主机的高权限环境。建议至少明确以下边界：

- 执行环境与承载 Agent 的主机分离；
- 不向沙箱注入不必要的密钥、令牌或内部配置；
- 将输入文件、输出文件和临时目录限定在任务所需范围；
- 对执行结果进行检查，不把沙箱输出直接当作可信操作指令；
- 代码执行失败、超时或行为异常时，进入可审计的拒绝或人工处理流程。

这里的“更强沙箱”是官方提出的安全方向，不代表材料指定了某一种实现。实际强度应由代码能力、数据敏感度、网络暴露面和业务后果共同决定。

### 2. 高风险任务默认隔离网络

当 Agent 可以读写内部系统或访问互联网时，提示词约束本身不能替代网络边界。作者建议将高风险工作负载放在默认拒绝的网络环境中，只为明确需要的服务开放受控访问。

同时要检查共享服务。易受攻击的共享组件可能成为 Agent 从受限环境进入其他系统的跳板。应清点任务依赖的服务，删除不必要的共享入口，避免多个任务共同使用无法区分的高权限身份。

### 3. 让权限随任务结束而失效

官方提到减少常驻权限。工程上可以将其转化为以下问题：

- Agent 是否长期持有数据库、文件系统或内部 API 凭据？
- 每个工具是否只暴露完成任务所需的动作？
- 只读任务是否错误地获得写权限？
- 是否能区分不同用户、任务和会话的授权？
- 任务结束、失败或被中止后，临时权限是否及时撤销？

最小权限不是单纯减少工具数量，而是同时限制工具的动作、资源范围、时间窗口和身份权限。

## 审计不只是记录“调用成功”

官方建议监控工具动作、可用推理信息和完整活动序列。作者建议每次调用至少关联任务、用户、会话、工具名称、参数摘要、结果状态和后续动作。敏感数据不应为了审计而无差别复制；日志设计要兼顾调查需要与数据暴露风险。

审计重点不是判断模型“说得是否合理”，而是还原它实际做了什么。例如：

- 是否调用了任务未授权的工具；
- 是否连续读取了与目标无关的资源；
- 是否尝试绕过网络、权限或审批边界；
- 是否出现批量读取、异常导出或破坏性操作；
- 工具返回异常后，Agent 是否继续扩大操作范围。

对“可用推理”的监控也应以合规、必要和可获得的信息为前提。给定材料没有规定必须记录哪一种内部推理内容，也没有规定具体日志格式，因此不应把某种实现方式声称为官方要求。

## 模拟攻击与版本变更验证

上线前验证不应只测试正常流程。应围绕官方列出的风险目标设计模拟攻击：

1. 构造未授权访问请求，确认 Agent 无法通过工具参数、路径或身份切换扩大权限。
2. 构造包含敏感数据的任务，确认 Agent 不会把数据导出到未授权位置。
3. 测试删除、覆盖、修改等破坏性工具是否受到权限和审批约束。
4. 检查提示词注入、恶意文件、异常工具返回是否能诱导 Agent 绕过防护。
5. 查看日志是否能完整还原攻击路径、工具动作和最终结果。
6. 对修复后的版本重复测试，确认边界没有因工具、模型或网络策略变更而失效。

模拟攻击结果应进入发布记录，并明确每项问题的影响范围、临时控制措施、修复责任人和复测结论。没有通过验证时，可以先关闭高风险工具或切换到人工确认，而不是让整个应用无条件获得完整能力。

## 一套可执行的上线决策框架

可以按三个问题进行发布判断：

**第一，Agent 能造成什么后果？**  
只生成文本的工作负载与能执行代码、读取内部数据或修改系统状态的工作负载，安全边界不同。后者应进入高风险审查范围。

**第二，Agent 能触达哪些资源？**  
列出互联网、内部网络、文件、数据库、共享服务和凭据。只要存在不必要的可达资源，就先收缩边界。

**第三，出了问题能否发现并停止？**  
如果没有足够的工具审计、活动序列和异常处置能力，即使权限看似有限，也不适合直接扩大上线范围。

工程团队可将结果分为三档：边界清晰、权限收敛且攻击验证通过，可以进入发布审批；部分控制已具备但仍有未验证路径，只开放低风险工具或小范围试运行；无法隔离代码执行、无法控制网络或无法还原关键活动，则暂停高风险能力。

## 最终检查清单

发布前逐项确认：

- [ ] 已识别 Agent 的工具、数据和系统影响范围。
- [ ] 模型生成代码及其他不可信代码使用更强隔离的沙箱。
- [ ] 高风险工作负载默认隔离互联网和内部网络。
- [ ] 不必要的共享服务已移除或从工作负载中断开。
- [ ] 常驻权限已减少，工具符合最小权限范围。
- [ ] 已建立工具动作、可见推理信息和完整活动序列的审计记录。
- [ ] 已配置针对未授权访问、数据窃取、破坏和绕过防护的检测。
- [ ] 上线前和版本变更后都完成模拟攻击及复测。
- [ ] 高风险工具存在暂停、人工审批或撤销权限的处置路径。
- [ ] 发布记录明确区分官方要求、内部控制和作者建议。
