# 用 GRPO 微调 LFM2.5-350M：提升结构化输出合规率的复现与评测方法

如果你需要在有限显存环境中，让小模型更稳定地输出 JSON、顶层数组或代码块，可以参考这套公开实验：使用约 500 条训练样本、TRL 的 GRPO 和 LoRA，在 16GB GPU 条件下训练 LFM2.5-350M 共 100 步，再通过 llama.cpp 的 OpenAI 兼容接口运行 IFStruct 评测。

**结论先说：**在相同的 llama.cpp BF16 服务栈和 2000 条 IFStruct 测试集上，文中基线总体通过率为 22.6%，GRPO 微调后为 29.7%，提高 7.1 个百分点。提升主要集中在 JSON 和裸数组任务，YAML 的变化很小。这个结果适合用来判断“任务专用奖励是否值得尝试”，不能直接当作你的业务 Schema 一定能达到的通过率。

本文区分三类信息：

- **官方发布事实：**来自 Hugging Face 这篇指南及其公布的训练、评测结果。
- **OpenLux 目录快照：**只用于补充检查模型或服务目录是否存在匹配。
- **作者建议：**结合复现过程和生产使用场景提出的操作建议。

## 这套方案解决什么问题

结构化输出的难点不只是“模型是否理解任务”，还包括是否严格遵守输出形式。例如，下游系统可能要求：

- 返回可解析的 JSON，而不是解释文字；
- 顶层必须是数组，而不是包裹在某个对象字段中；
- 对象必须包含指定数量的顶层字段；
- 字段类型、枚举值和嵌套结构必须符合 JSON Schema；
- 内容必须放在 fenced code block 中，或明确要求不能使用代码块。

指南采用三个奖励函数分别衡量这些问题：

1. **JSON 格式奖励：**判断输出是否可解析，以及是否符合要求的裸 JSON 或 fenced code block 形式；
2. **字段数量奖励：**判断顶层字段数量是否与目标一致，数量偏差越大，得分越低；
3. **Schema 验证奖励：**根据 JSON Schema 的约束违反情况评分，并关注必填字段是否覆盖。

三个奖励的权重分别为 `1.0`、`0.5` 和 `2.0`。这意味着 Schema 合规在总奖励中占据更高权重，但格式和字段数量仍会影响训练方向。

## 官方实验的复现配置

官方指南使用 `LiquidAI/LFM2.5-350M`，通过 TRL 的 GRPO 训练，并挂载 LoRA 适配器。LoRA 目标模块覆盖该模型使用的注意力和混合架构相关模块：

```python
target_modules=[
    "q_proj", "k_proj", "v_proj", "out_proj",
    "in_proj", "w1", "w2", "w3",
]
```

LoRA 配置中的关键参数包括：

| 项目 | 指南中的配置或事实 | 复现时的含义 |
|---|---:|---|
| LoRA `r` | 16 | 适配器秩 |
| `lora_alpha` | 32 | LoRA 缩放参数 |
| 训练参数量 | 约 600 万 | 约占模型参数的 1.66% |
| 训练样本 | 约 500 条 | 小规模任务专用数据 |
| 训练步数 | 100 | 公开实验的训练预算 |
| 每组生成数 | 8 | GRPO 对同一提示采样多个补全 |
| GPU 条件 | 面向免费档 16GB GPU | 适用于低显存试验 |
| 学习率 | `5e-5` | 指南中的训练参数 |
| 预热步数 | 10 | 指南中的训练参数 |
| 最大补全长度 | 1024 | 为嵌套 JSON 留出空间 |
| 温度 | 1.1 | 保持同组采样差异 |
| KL 系数 | `0.01` | 约束策略偏离参考模型 |

训练数据来自结构化输出指令数据集，包含提示、目标 JSON Schema 和预期字段数量。为了弥补训练数据与 IFStruct 评测任务之间的差异，指南还做了两类增强：

- 约 40% 的提示增加 fenced code block 要求；
- 约 20% 的样本改造成顶层数组任务，并要求满足数组元素数量。

这一步值得重视。若训练数据只包含普通 JSON 对象，模型可能学会“输出 JSON”，但仍然不擅长裸数组、代码块或精确元素数量等边界格式。

## 如何设计适合业务的奖励

复现时，不建议只复制 Schema 验证奖励。更稳妥的做法是先把失败类型拆开，再决定奖励权重。

### 第一层：可解析和外形

先判断输出是否能被解析。如果业务要求的是裸数组，就要把对象包裹数组、附带说明文字等情况单独记为失败或部分得分。如果业务允许 fenced code block，则需要先提取代码块，再解析其中内容。

这一层反映的是“输出能否进入解析器”，适合捕获最直接的格式错误。

### 第二层：字段和数量

对于对象，检查顶层字段数量；对于数组，检查元素数量。字段数量奖励不能替代 Schema 验证，但可以帮助模型更早学会控制输出规模。

需要注意，字段数量正确并不代表字段名、类型或嵌套结构正确。因此它应当是辅助奖励，而不是主要验收标准。

### 第三层：Schema 合规

使用每条样本对应的 JSON Schema 验证输出，并记录具体错误类型，例如：

- 必填字段缺失；
- 字段类型不匹配；
- 出现额外字段；
- 数组元素数量不符合约束；
- 枚举值不在允许范围内；
- 数值超出上下限。

建议保存每一类错误，而不是只保存一个总分。总分可以判断训练是否带来变化，错误分布才有助于判断下一轮数据应该补什么。

## 评测链路：llama.cpp 加 OpenAI 兼容接口

官方指南先用 BF16 GGUF 运行基线模型，再将合并后的模型转换为 BF16 GGUF，使用 llama.cpp 启动本地服务。基线服务的关键参数如下：

```bash
llama-server \
  -hf LiquidAI/LFM2.5-350M-GGUF:BF16 \
  -c 32768 \
  -np 4 \
  -ngl 99 \
  --alias LiquidAI/LFM2.5-350M \
  --host 127.0.0.1 \
  --port 8080
```

其中，`--alias` 对应评测器发送的模型名，`-np 4` 表示并行处理四个请求，`-c 32768` 设置上下文长度，`-ngl 99` 请求在可用时将层卸载到 GPU。

IFStruct 评测通过本地 `/v1` 端点访问模型：

```bash
uv run ifstruct-eval \
  --model LiquidAI/LFM2.5-350M \
  --base-url http://localhost:8080/v1 \
  --api-key dummy \
  --dataset data/test.jsonl \
  --results-file results/lfm2.5-350m-llamacpp-base.json \
  --n-threads 4 \
  --max-tokens 2048 \
  -v
```

这里的 `--api-key dummy` 只是本地评测命令中的占位值，不能据此推断线上服务不需要认证，也不能推断任何第三方 API 的认证方式。

合并 LoRA 后，指南使用 `convert_hf_to_gguf.py` 转换为 BF16 GGUF，再通过另一个端口启动服务：

```bash
llama-server \
  -m ./models/lfm25-350m-grpo-bf16.gguf \
  --alias lfm25-350m-grpo-structured-output \
  -c 32768 \
  -np 4 \
  -ngl 99 \
  --host 127.0.0.1 \
  --port 8081
```

评测时把 `--base-url` 改为 `http://localhost:8081/v1`，并替换 `--model` 和结果文件路径。这样可以在相同服务参数下比较基线和微调模型，减少部署差异造成的干扰。

## 公开结果应该如何解读

官方公布的对比结果如下：

| 评测分组 | 基线 | GRPO 微调后 | 变化 |
|---|---:|---:|---:|
| Overall | 22.6% | 29.7% | +7.1 个百分点 |
| JSON | 18.0% | 31.9% | +13.9 个百分点 |
| YAML | 27.2% | 27.5% | +0.3 个百分点 |
| Wrapper key | 28.5% | 29.7% | +1.2 个百分点 |
| Bare list | 16.6% | 29.7% | +13.1 个百分点 |

训练目标与结果变化基本对应：训练中加入了 fenced code block 和顶层数组任务后，JSON 与裸数组通过率改善明显，而 YAML 几乎没有变化。

不过，不能把这组结果直接外推到生产业务。原因包括：

- 训练数据与 IFStruct 测试集分布不同；
- 你的 Schema 复杂度、字段命名和内容类型可能不同；
- 服务端解码、提示模板和最大输出长度会影响结果；
- 公开实验只说明这套配置在该评测设置下有效，不代表所有结构化任务都同比提升。

官方基线统计中，常见错误包括必填字段缺失、数组元素数量错误、类型不匹配、代码块未闭合和额外字段。微调后仍然存在必填字段缺失等问题，因此“通过率提高”不等于已经满足生产验收条件。

## 一套可执行的迁移与验证步骤

### 1. 固定业务 Schema 和输出协议

先明确每个接口是要求裸对象、裸数组、代码块还是其他形式。把“是否允许解释文字”“是否允许额外字段”“数组元素数量”写进验证器，而不是只写在自然语言提示中。

### 2. 建立基线集

从真实业务请求中抽取或构造一组脱敏样本，覆盖正常输入、边界输入、长文本、嵌套对象、数组和枚举字段。至少同时记录：

- 可解析率；
- 格式匹配率；
- 字段数量匹配率；
- Schema 通过率；
- 每种验证失败的数量。

### 3. 先做 100 步小规模试验

按照指南的 16GB GPU 配置运行 100 步，先验证训练链路、显存占用、LoRA 合并和 GGUF 转换是否正常。不要在没有基线的情况下仅看训练奖励上升就判断模型可用。

### 4. 让训练分布覆盖生产格式

如果生产接口需要顶层数组，就加入数组任务；如果要求代码块，就加入代码块任务；如果 Schema 有严格枚举和数量约束，也应在训练样本中出现。训练样本数量较少时，格式覆盖比盲目扩大样本量更容易解释效果来源。

### 5. 使用同一服务栈复测

基线和微调模型都使用相同的 llama.cpp、量化或精度、上下文长度、并发数、最大输出长度和评测集。只有这样，结果差异才主要反映微调影响。

### 6. 按失败类型决定是否上线

如果总体通过率提高，但必填字段缺失仍然是主要问题，应该优先补充必填字段示例和相关奖励，而不是只看总分。上线前还要设置解析失败、Schema 失败和重试策略，不能把模型输出直接视为可信结构。
