# 企业知识库答非所问怎么办：先测检索召回，再决定是否加 Rerank

## 把问题拆成三个可以观察的环节

阿里云的[Rerank 接口文档](https://www.alibabacloud.com/help/en/model-studio/text-rerank-api)说明，重排模型会重新评分初次检索返回的候选文档。这个定义意味着：相关资料如果根本没有进入候选集，单靠重排无法把它找回来。

先保存用户问题、初次召回列表、重排列表与最终引用。不要只保存最后的模型回答，否则无法判断答案中的错误来自哪一步。每个片段保留文档 ID、版本、章节和更新时间，避免相似内容被误认成同一来源。

对于“目前支持哪种配置”之类的问题，还要确认资料是否仍然有效。历史版本可能与问题词汇高度相似，但业务上已经失效；这种情况优先处理资料版本与过滤规则。

## 准备一份有标准证据的题集

选二十到三十个来自真实需求的问题，为每题标注可以回答它的文档或段落。这个规模适合首轮诊断，不是模型效果保证。题目应同时包含常见问法、同义表达、产品名缩写和明确没有答案的问题。

标注时允许一个问题对应多个有效来源。如果团队对正确来源都无法达成一致，先整理资料，不宜把分歧算作模型错误。没有答案的题目单独检查拒答与证据缺失提示，不混入正例召回率。

| 题目类型 | 需要检查的内容 | 容易暴露的问题 |
|---|---|---|
| 精确产品编号 | 对应型号是否出现 | 只做语义检索导致编号丢失 |
| 同义表达 | 相同含义能否召回 | 依赖字面匹配 |
| 版本问题 | 有效版本是否排在前面 | 旧资料未过滤 |
| 多条件问题 | 所需证据是否齐全 | 只召回其中一个条件 |
| 无答案问题 | 是否明确缺少资料 | 模型用猜测补空白 |

## 先算证据有没有进入候选集

对标注了相关文档的题目，可以计算 Recall@K：前 K 个候选中包含的相关文档数量，除以该题全部已标注相关文档数量。下面是离线示例，只处理文档 ID，不会调用任何付费接口。

```python
def recall_at_k(ranked_ids, relevant_ids, k):
    if type(k) is not int or k < 0:
        raise ValueError("k 必须是非负整数")
    relevant = set(relevant_ids)
    if not relevant:
        return None
    return len(set(ranked_ids[:k]) & relevant) / len(relevant)

assert recall_at_k(["a", "b", "c"], {"b", "c"}, 2) == 0.5
assert recall_at_k(["b", "b"], {"b", "c"}, 2) == 0.5
assert recall_at_k(["a"], set(), 1) is None
```

同一片段重复出现不应重复加分。题集中无答案的样本返回未知指标，单独统计，不能为了好看把它记作完全召回。对长文档还可以把统计单位细化为段落，避免整篇文档命中掩盖真正证据没被送入上下文。

## 根据失败位置决定改什么

| 观察结果 | 优先尝试 | 需要保留的对照 |
|---|---|---|
| 正确文档不在索引里 | 补齐或修复资料导入 | 导入前后文档清单 |
| 索引有文档，但召回不到 | 调整切分、查询或检索方式 | 相同题目的候选列表 |
| 候选里有正确证据，排序靠后 | 测试重排或版本过滤 | 重排前后前 K 名 |
| 证据已靠前，回答仍然错误 | 检查提示词与引用组织 | 实际送给生成模型的内容 |

每轮只改变一个主要条件。若同时更换切分规则、向量模型、重排模型和提示词，即使结果提升，也很难知道是哪一步起作用。先记录一个能复现的基线，再扩大实验范围。

## 增加重排之前先设成本和延迟边界

重排要处理候选材料，候选数量与片段长度都会影响资源消耗。具体每次允许多少文档、每条长度及费用，以所选服务的当前文档为准；不要把其他模型的限制直接照搬。

可以在相同题集上比较两三组候选数量，同时记录检索耗时、重排耗时、生成耗时及最终证据命中。更大的候选集可能增加找到证据的机会，也可能让处理变慢，需要看整体业务是否接受。

权限过滤应在资料进入用户可见上下文之前生效。不要为了提高召回指标，把其他部门或其他客户的私有文档混进候选集。评估的目标是在允许访问的范围内找到正确证据。

## 怎样把测试结果转成上线决定

评估表保留每题是否命中、引用是否有效、回答是否完整，以及各阶段费用。先修复成批出现的同类错误，再考虑换更强的生成模型。上线前保留一组未参与调参的题目，检查改动能否适用于新问题。

如果首轮实验发现大多数错误来自旧文档，可以把“整理版本与生效时间”作为下一步，而不是立刻增加新组件。资料清楚、评估可复现，后续投入才容易衡量。
