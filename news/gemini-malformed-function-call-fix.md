# Gemini 函数调用返回 MALFORMED_FUNCTION_CALL 怎么办：调用前的结构化文本、宽松参数结构与调用模式改法

用 Gemini API 做函数调用（工具调用）时，有时请求没有报 HTTP 错误，响应里却既没有 `functionCall`，也几乎没有文本，`finishReason` 是 `MALFORMED_FUNCTION_CALL`。官方 API 参考对它的定义是「模型生成的函数调用无效」（The function call generated by the model is invalid）。在代理循环（agent loop）里，这种情况看起来就像模型「什么都没说就停了」。

直接结论：这不是 Key、地址或额度问题，重发同一个请求也可能时好时坏。按官方文档，常见的改法有三类：不要让模型在调用工具前先输出 JSON/XML/YAML 之类的结构化文本；把参数结构写得更具体（明确类型、键名不带空格和特殊字符）；在必须调用工具的步骤里改用 `ANY` 模式。另外，代码要把这个 `finishReason` 当成单独的分支处理，而不是当成正常结束。

本文依据 Google 官方的 [函数调用文档](https://ai.google.dev/gemini-api/docs/function-calling)、[generateContent API 参考](https://ai.google.dev/api/generate-content)、[Gemini 3.8 Flash 新特性与迁移清单](https://ai.google.dev/gemini-api/docs/whats-new-gemini-3.8) 和 [Gemini API 更新日志](https://ai.google.dev/gemini-api/docs/changelog)，适用于用 `generateContent` / `streamGenerateContent` 或 Interactions API 做函数调用的场景。

## 一、为什么最近更容易碰到

Gemini API 更新日志 2026 年 10 月 8 日的条目写明：`gemini-3.7-flash` 已弃用，对它的 API 调用会被自动转到 `gemini-3.8-flash`；`gemini-3.5-flash` 也已弃用，调用会被自动转到 `gemini-3.6-flash`。也就是说，直接调用 Google API 时，代码里模型名没改，实际服务的模型已经换了。

而 Gemini 3.8 Flash 的迁移清单在「函数调用」一项里专门写了：如果遇到和「工具调用前的文本」有关的 `Malformed_Function_Call` 错误，去看函数调用文档里的「Workarounds for pre-tool text requirements」（工具调用前文本要求的变通办法）。同一份清单还要求：多模态内容放进函数结果里返回；内嵌指令用 `\n\n` 分隔；只用 generateContent 接口时，每个 `FunctionResponse` 都要带上 `call_id` 和 `name`。

所以如果你的工具调用以前正常、最近开始出现这个 `finishReason`，先确认请求里的模型名是不是已被改道的旧名，再按下面几节逐项排查。

## 二、先确认是不是这个问题：看 finishReason 和 finishMessage

打印响应里第一个候选的 `finishReason`（Python SDK 里是 `candidates[0].finish_reason`）。API 参考说明，`finishMessage` 字段会「说明模型停止生成的原因」，并且只在 `finishReason` 有值时才会填。下表列出几个容易和它混在一起的结束原因，说明一栏是官方原文的意思：

| finishReason | 官方说明 | 先查什么 |
|---|---|---|
| `MALFORMED_FUNCTION_CALL` | 模型生成的函数调用无效 | 本文第三到五节：调用前文本、参数结构、调用模式 |
| `UNEXPECTED_TOOL_CALL` | 模型生成了工具调用，但请求里没有启用任何工具 | 这一轮请求是否漏传了 `tools` |
| `TOO_MANY_TOOL_CALLS` | 模型连续调用了太多工具，系统退出执行 | 代理循环是否反复调用同一工具、提示词是否给了结束条件 |
| `MISSING_THOUGHT_SIGNATURE` | 请求里至少缺了一个思维签名 | 回传历史时是否改动或丢掉了模型返回的部分（见第六节） |
| `MAX_TOKENS` | 达到请求里设置的最大 token 数 | 调大或去掉输出上限 |

确认是 `MALFORMED_FUNCTION_CALL` 后，把 `finishMessage` 记下来。在 Google 官方 python-genai 仓库的 [issue #3230](https://github.com/googleapis/python-genai/issues/3230) 中，报告者给出的 `finishMessage` 以 `Malformed function call: call:default_api:create_pages{...` 开头，能看到模型实际写出的那段调用，以及带空格的键名没有加引号。对照这段文字，通常能看出是哪个参数出了问题。

## 三、原因一：提示词要求模型在调用工具前先输出结构化文本

函数调用文档的「Workarounds for pre-tool text requirements」一节写道：如果提示词让模型在调用工具之前先输出 XML、YAML、JSON 这类结构化文本，工具调用偶尔会以 `Malformed_Function_Call` 失败。官方给了三种改法，第一种标为首选：

1. **首选**：让模型把调用前的说明写进一个专门的 `update()` 函数调用，而不是直接输出文本。官方示例要求模型「在调用任何其他工具之前，每次回复都必须先调用 `update`」，`update` 有 `previous_step`、`plan`、`next_step`、`external` 四个字符串参数。这样模型会在同一步里发出两个调用（先 `update`，再真正的工具）。
2. 让模型把说明写成 Markdown 标题形式（例如 `# UPDATE`、`## PLAN`），不要写成结构化文本。
3. 干脆不要求模型在调用工具前输出文本。

排查时搜一下系统提示词里有没有「先输出 JSON 计划」「先用 XML 写思路」之类的要求，有的话按上面三种改法之一去掉或改写。

## 四、原因二：参数结构太宽松（无类型 object、开放键名）

函数调用文档「最佳实践」一节的相关要求是：命名用描述性的名字，不带空格或特殊字符；使用具体类型（integer、string、enum）；同时启用的工具控制在 10～20 个以内。「注意事项与限制」一节还写明只支持 OpenAPI schema 的一个子集。

前面提到的 issue #3230 是一个具体例子：参数 `pages` 声明为 `{"type": "array", "items": {"type": "object"}, "maxItems": 100}`，`items` 是没有声明任何属性的 object，提示词又要求模型填入「Incident Title」这种带空格的键名。报告者用 `gemini-3.8-flash` 在 `AUTO` 模式下每种写法各跑 20 次：原始写法 14 次出现 `MALFORMED_FUNCTION_CALL`；把键名改成不带空格的 `IncidentTitle` 后仍有 8 次；在这个最小示例里去掉 `maxItems` 后为 0 次，但报告者说在真实的 Notion MCP 工具上去掉 `maxItems` 并没有解决问题。仓库维护者回复已复现，判断问题出在服务端 `AUTO` 模式的函数调用生成与解析，不在 SDK，并已在内部升级处理。截至本文写作时该 issue 仍未关闭，官方没有给出修复时间。

在官方修复之前，可以按最佳实践收紧参数结构：

- 给 object 写出 `properties` 和每个属性的类型，能用 `enum` 的字段（如「低/中/高」）用 `enum`。
- 键名用英文、驼峰或下划线，不带空格、冒号、括号；需要展示给人看的名称放到值里。
- 键名确实无法预先确定（例如按用户表格列名动态生成）时，issue 报告者的做法是把这类自由结构的参数声明成字符串，让模型传 JSON 文本，再由你的代码解析。这是报告者的变通做法，不是官方文档的建议，解析失败时要有兜底。
- 接 MCP 工具时注意：函数调用文档要求 MCP 服务器名不要含 `-`，改用 snake_case。

## 五、改法三：按场景选择函数调用模式

generateContent 接口在 `toolConfig.functionCallingConfig.mode` 里设置调用模式（Interactions API 对应 `generation_config.tool_choice`）。API 参考对各模式的说明：

- `AUTO`（默认）：模型自己决定是调用函数还是用自然语言回答。
- `ANY`：模型被限定为只能预测函数调用；配合 `allowedFunctionNames` 可以限定只调用其中某几个函数（这个字段只应在 `ANY` 或 `VALIDATED` 模式下设置）。
- `VALIDATED`：模型可以调用函数也可以回答文本，但会用约束解码校验函数调用。
- `NONE`：不预测任何函数调用，效果等同于没传函数声明。

如果某一步按业务逻辑一定要调用工具（例如「把这些记录写入表格」），可以改用 `ANY` 并用 `allowedFunctionNames` 指定函数。issue #3230 中报告者和维护者的测试里，改用 `ANY` 后都没有再出现该错误。如果这一步模型既可能调用工具也可能直接回答，可以对比测试 `VALIDATED`。注意函数调用文档提到，`ANY` 模式下 API 可能拒绝过大或嵌套过深的 schema，改模式后如果开始报错，先简化参数结构。

## 六、多轮回传：FunctionResponse 的 call_id、name 与思维签名

格式错误也可能出在你回传给模型的历史里。按 Gemini 3.8 Flash 迁移清单，只用 generateContent 接口时，要确保每个 `FunctionResponse` 都带有 `call_id` 和 `name`；Interactions API 里对应的是 `function_result` 步骤，`call_id` 取自函数调用步骤的 `id`，`name` 与调用一致。

思维签名方面，思考文档说明：在 generateContent 接口里，签名可以附在任意部分上，包括 `functionCall` 部分；自己维护历史（无状态模式）时，必须把模型返回的思考内容原样回传，不要删除或修改，切换模型时也要回传上一个模型的思考内容。如果 `finishReason` 是 `MISSING_THOUGHT_SIGNATURE`，就检查拼历史的代码有没有只取了文本、丢掉了其他部分。

## 七、验证方法与代码里的兜底

这类错误是概率性的，单次请求成功不能说明已经修好。建议这样验证：

1. 固定一组会触发问题的真实输入，同一请求重复发送多次（issue 中每个变体跑了 20 次），统计 `finishReason` 的分布。
2. 修改后，成功标准是：该组输入里不再出现 `MALFORMED_FUNCTION_CALL`，候选内容里有 `functionCall` 部分，参数能被你的代码正常解析。
3. 在代理循环里单独处理这个 `finishReason`：记录 `finishMessage` 和请求内容，不要把它当成模型正常结束。官方最佳实践也要求在执行前校验函数调用、做好错误处理。
