# Claude Managed Agents 新增 `auto` 权限策略：让服务器评估并审批工具调用

结论先说：`auto` 适合希望把 Claude Managed Agents 的工具调用判断交给服务器处理，同时保留拒绝和人工审批分支的团队。它尤其适用于使用 MCP 工具、需要记录调用评估结果，或已有人工审批流程的 Agent 系统。

本文面向三类读者：负责 Managed Agents 配置的工程师、需要治理 MCP 工具调用的安全团队，以及正在检查工具审批事件处理逻辑的开发者。需要先明确边界：官方发版说明确认了 `auto`、服务器评估行为和事件字段，但提供的材料没有给出完整请求示例、字段内部结构、审批接口细节、价格或可用范围。因此，本文只说明已确认的行为和可执行的验证方法，不补写未公开的参数。

## 官方发布了什么

根据 Claude Platform 2026 年 9 月 10 日的官方发版说明，Claude Managed Agents 的 permission policies 新增 `auto`。

使用该策略时，服务器会评估每一次 Agent 工具调用或 MCP 工具调用，并根据评估结果采取三类动作：

- 执行调用；
- 拒绝调用；
- 暂停调用，等待批准。

这里的关键变化不是简单增加一个“允许”或“拒绝”开关，而是把每次调用的处理交给服务器评估。对于接入外部系统的 Agent，这意味着调用结果不应只按“模型是否请求了工具”来判断，还要处理服务器作出的后续决定。

官方同时说明，`agent.tool_use` 和 `agent.mcp_tool_use` 事件会在 `evaluation` 字段中报告调用评估结果，并提供 `evaluated_permission`。这两个字段是后续审计、状态机处理和人工审批衔接的重点。

## `auto` 的调用生命周期

一个工具调用进入系统后，建议按“请求、评估、分支、记录”四步理解：

1. Agent 发起工具调用，调用对象可能是普通 Agent 工具，也可能是 MCP 工具。
2. 服务器对这次调用进行评估。
3. 服务器根据评估结果执行、拒绝，或暂停并等待批准。
4. 系统从对应事件的 `evaluation` 和 `evaluated_permission` 中读取结果，并推进业务状态。

需要注意，暂停等待批准不是成功，也不是拒绝。它代表调用尚未完成，业务系统必须保留待处理状态，等待批准动作或后续事件。否则，系统可能把暂停误认为调用失败，或者重复提交同一调用。

官方材料确认了评估字段存在，但没有在输入材料中列出 `evaluation` 的内部结构或 `evaluated_permission` 的具体取值。因此，接收端不应只依赖未经确认的字符串值进行判断。更稳妥的做法是先记录原始事件，再根据实际文档和测试响应建立明确的状态映射。

## 如何检查现有权限策略

迁移前先盘点现有 Managed Agents，而不是直接切换策略。至少检查以下内容：

- 当前 Agent 使用的工具权限策略；
- 工具清单中哪些属于 MCP 工具；
- 调用事件消费方是否已经处理 `agent.tool_use` 和 `agent.mcp_tool_use`；
- 当前系统是否区分“调用完成”“调用拒绝”和“等待处理”；
- 是否已有人工审批人、审批队列或审批记录；
- 发生拒绝时，Agent 会话和业务流程是否能正常结束或继续；
- 事件处理是否保留原始 `evaluation` 与 `evaluated_permission`。

如果现有系统默认把所有工具调用当作同步成功流程，切换到 `auto` 前应优先改造状态处理。因为服务器可能暂停调用，调用方不能假设收到工具请求后立即得到工具结果。

## 人工审批流程应如何接入

官方确认服务器可以暂停调用等待批准，但提供材料没有规定你的业务审批系统必须采用哪种接口。因此，人工审批部分应按自身系统设计，并围绕事件状态建立可追踪流程。

一个可操作的流程是：

1. 接收到工具调用事件后，保存事件标识、工具类型、时间、会话上下文，以及 `evaluation` 和 `evaluated_permission`。
2. 发现调用处于等待批准状态时，创建一条待审批记录。
3. 向具备相应权限的审批人展示必要信息，包括调用对象和评估结果。
4. 审批人执行允许或拒绝操作，并记录人员、时间和决定。
5. 让 Managed Agents 会话继续等待中的调用，或按照官方接口要求提交批准结果。
6. 对批准后的实际执行结果、拒绝后的终止或继续行为分别记录。
7. 对超时、重复事件和审批结果不一致的情况进行告警和人工复核。

这里有一个重要的实现原则：审批记录和工具执行记录要分开。批准表示“允许继续”，不等于工具已经成功执行。拒绝也不应只记录在界面上，还应让业务流程明确知道该调用没有执行。

官方发版材料还提到，`ant beta:sessions connect` 可以把终端连接到 Managed Agents 会话，实时跟随会话、发送消息，并允许或拒绝等待批准的工具调用；传入 `--web` 时，可以在本地提供会话查看器并打开 Claude Console 的会话界面。这可以作为人工处理路径的一个官方工具入口，但不应据此推断它替代了团队自己的审批系统。

## 事件读取与验证重点

围绕两个事件类型，建议分别建立测试用例：

- `agent.tool_use`：验证普通 Agent 工具调用是否包含 `evaluation` 和 `evaluated_permission`；
- `agent.mcp_tool_use`：验证 MCP 工具调用是否以相同方式报告评估结果。

每个测试至少覆盖三条分支：

| 测试分支 | 要确认的结果 | 业务系统应做的事 |
|---|---|---|
| 服务器允许并执行 | 调用继续执行，事件含评估字段 | 记录评估结果，并等待工具执行结果 |
| 服务器拒绝 | 调用没有按正常路径执行 | 记录拒绝原因或评估信息，验证 Agent 和业务流程的收尾 |
| 服务器暂停 | 调用进入等待批准状态 | 创建审批任务，避免重复执行，等待批准处理 |

由于输入材料没有给出字段的完整数据结构，验证时应直接观察实际事件，而不是先假设字段格式。建议在测试环境中保存完整原始事件，同时生成经过解析的结构化日志。这样既方便排查字段变化，也能确认解析失败时不会把未知状态错误归类为“允许”。

## 迁移决策框架

是否切换到 `auto`，可以从四个问题判断：

1. **治理需求**：是否需要服务器对每次工具调用作出评估？
2. **流程能力**：系统是否能处理执行、拒绝和暂停三种状态？
3. **审批责任**：等待批准的调用由谁处理，审批结果如何留痕？
4. **回滚准备**：切换后出现字段解析或流程兼容问题，是否能恢复原策略并保留诊断信息？

如果只有第一个问题的答案是“是”，但后面三个问题尚未解决，建议先完成事件记录和分支测试，再调整权限策略。对于涉及外部系统或高影响操作的 MCP 工具，人工审批链路尤其需要先验证暂停和拒绝行为。
