# OpenAI API 零数据保留：符合资格客户上线前需核对的边界

如果你正在为企业系统评估 **OpenAI API 的 Zero Data Retention（ZDR）**，先记住三个结论：

1. **ZDR 不是默认对所有 API 客户开放的配置**，需要先向 OpenAI 核对资格。
2. 符合条件并采用 ZDR 部署后，处理完成不保留 prompt 和模型响应，客户内容也不供 OpenAI 人员审阅；但这不等于所有数据类型都没有例外。
3. **疑似 CSAM 的图片仍可能被保留，用于人工审查和依法报告**。这项例外必须单独写进数据合规说明和上线审批材料。

本文适合负责 API 选型、隐私评估、数据合规、架构设计和上线验收的团队。下文将区分 OpenAI 官方发布事实、OpenLux 目录快照和作者建议，不把中转服务或规划中的能力当成已经生效的 ZDR 条款。

## 一、官方所说的 ZDR 覆盖什么

根据 OpenAI 于 2026 年 8 月 19 日发布的信息，符合资格的 API 客户可使用 Zero Data Retention。其核心承诺包括：

- 请求处理完成后，不保留 prompt；
- 请求处理完成后，不保留模型响应；
- 客户内容不供 OpenAI 人员审阅；
- 企业数据默认不用于训练；
- ZDR 部署的内容保留在客户控制的基础设施中。

这些事实分别涉及请求内容、人工访问、训练用途和部署位置，不能简单合并成“任何相关数据都不留存”。在合同、隐私说明和内部评审中，建议逐项记录对应范围，而不要只写一句“使用 ZDR，因此不保存数据”。

还需要注意，官方同时说明，OpenAI 正在开发一种新选项：数据存放于 OpenAI 基础设施，但使用客户控制的密钥加密。该选项属于开发中的方案，不能在当前上线材料中当作已经可用的部署能力。

## 二、第一道门槛：先确认客户是否符合资格

“符合资格的 API 客户”是官方表述中的必要条件。材料没有给出一份适用于所有客户的公开资格清单，因此企业不应仅凭账号类型、采购规模或自身合规要求，自行判断已经获得 ZDR。

建议在上线前向 OpenAI 书面核对以下事项：

| 核对项目 | 需要确认的问题 | 未确认时的处理 |
|---|---|---|
| 客户资格 | 当前 API 客户是否被批准使用 ZDR | 暂不把 ZDR 写入正式承诺 |
| 适用范围 | ZDR 是否覆盖计划使用的 API 场景和部署方式 | 逐场景拆分评估 |
| 数据范围 | prompt、模型响应及相关内容分别如何处理 | 不扩大官方原始表述 |
| 基础设施 | 内容是否确实保留在客户控制的基础设施中 | 要求架构和条款对应 |
| 例外 | 疑似 CSAM 图片如何保留、审查和报告 | 单列为强制例外 |
| 新能力 | 客户控制密钥方案是否已经可用 | 按“开发中”处理 |

如果无法取得明确确认，团队可以继续做技术评估，但不宜在对外隐私政策、客户合同或采购承诺中写成“已启用 ZDR”。

## 三、ZDR 不等于没有任何数据保留例外

本文最需要单独强调的边界是：**疑似 CSAM 的图片，即使在 ZDR 部署中，也仍会保留，以供人工审查和依法报告。**

这意味着数据分类不能只按“是否使用 ZDR”进行。对于包含图片的业务，至少应增加一条独立判断：

- 是否可能接收或生成图片；
- 是否存在疑似 CSAM 内容的处理路径；
- 该类内容是否可能触发保留；
- 保留目的是否为人工审查和依法报告；
- 合规说明是否明确写出该例外。

这里不要把“客户内容不供 OpenAI 人员审阅”理解为无条件适用于所有内容。官方材料已经明确给出了疑似 CSAM 图片的人工审查例外，因此上线文档应同时呈现一般规则和特殊规则，避免形成过度承诺。

对于纯文本或其他数据类型，也不应从本文材料外推出未说明的保留细节。若业务依赖具体的日志、滥用检测、调试或审计行为，应直接向 OpenAI 索取与自身场景对应的正式说明。

## 四、部署位置和密钥方案要分开评估

官方信息指出，ZDR 部署的内容保留在客户控制的基础设施中。这一描述对有数据驻留要求的企业很重要，但“客户控制”仍应落实到架构图和责任边界中。

评估时建议分别回答：

1. 哪些内容由客户系统接收、处理和保存；
2. API 请求中哪些字段属于客户内容；
3. 哪些组件位于客户控制的基础设施内；
4. OpenAI 侧当前承诺覆盖到哪一步；
5. 计划中的客户控制密钥方案是否已正式推出并可签约。

客户控制密钥、存放于 OpenAI 基础设施的方案目前仍处于开发阶段。它与“内容保留在客户控制的基础设施中”是两种不同的架构选项，不能在设计文档中混为一谈。

## 五、Private Safety Processing 目前应按规划能力处理

OpenAI 还说明，Private Safety Processing 正由早期客户测试，计划在 2026 年 9 月开始推出并发布技术白皮书。其目标是：在不让 OpenAI 人员访问底层内容的情况下，跨关联交互识别风险，并只返回有限的安全信号。

由于材料将其描述为早期测试和计划推出的能力，企业当前不应把它当成已经普遍可用的 ZDR 附件，也不应在上线前据此改变现有安全架构。更稳妥的做法是：

- 先维持当前已批准的内容安全和人工复核流程；
- 等正式推出后，核对白皮书中的处理范围、输入输出和限制；
- 再判断它是否适用于需要关联多次交互的业务；
- 将其能力边界与 ZDR 的数据保留承诺分开记录。

Private Safety Processing 关注的是安全检测方式，ZDR 关注的是数据保留和访问边界，两者不是同一个开关。

## 六、不要把独立中转服务解释成 OpenAI 端到端 ZDR

在本次公开目录快照中，OpenLux 的匹配结果为空：`[]`。这只能说明该目录快照没有给出相应匹配，不能证明任何 OpenAI API 客户已经获得 ZDR，也不能证明通过独立中转服务即可自动取得 OpenAI 端到端 ZDR。

因此，若架构中存在中转、代理或网关服务，应分别核查：

- 中转服务是否保存请求或响应；
- 数据是否经过额外处理；
- 中转服务的控制方是谁；
- OpenAI 侧的 ZDR 资格和部署承诺是否仍由 OpenAI 单独确认。

作者建议：不要把“使用某个中转服务”写成“已满足 OpenAI ZDR”，除非企业已经取得与自身客户资格、部署方式和数据范围相对应的正式确认。

## 七、上线前的验证与迁移步骤

可以按下面顺序推进，而不是先改代码、再补合规材料：

### 1. 盘点数据流

列出 prompt、模型响应、图片及其他客户内容的来源、去向和保存位置。特别标记图片输入和跨请求关联场景。

### 2. 获取资格确认

向 OpenAI 核对当前 API 客户是否符合 ZDR，并要求确认目标部署方式是否在适用范围内。将答复保存到采购、隐私和安全评审记录中。

### 3. 建立例外清单

把疑似 CSAM 图片的保留、人工审查和依法报告单独列出，不要埋在“ZDR 不留存”的概括性表述里。

### 4. 对齐架构责任

确认内容是否按计划保留在客户控制的基础设施中，并区分当前方案与仍在开发的客户控制密钥方案。

### 5. 复核安全能力

Private Safety Processing 在正式推出并发布技术白皮书前，只作为待评估能力。不要用计划中的能力替代当前控制措施。

### 6. 做上线签字检查

由技术、隐私、法务和安全负责人共同确认：资格、部署、数据范围、例外、第三方中转和对外表述均一致。

## 八、最终检查清单

上线前至少应能对以下问题给出“有依据的答案”：

- [ ] 是否已向 OpenAI 确认客户具备 ZDR 资格？
- [ ] 是否明确 ZDR 覆盖 prompt 和模型响应的处理后保留规则？
- [ ] 是否记录企业数据默认不用于训练这一事实，而没有扩大为其他承诺？
- [ ] 是否核对内容保留在客户控制基础设施中的部署安排？
- [ ] 是否把客户控制密钥方案标记为开发中，而非当前可用功能？
- [ ] 是否单独写明疑似 CSAM 图片的保留、人工审查和依法报告例外？
- [ ] 是否避免把 Private Safety Processing 的计划推出当成已上线能力？
- [ ] 是否确认任何中转服务都不会被误写成 OpenAI 端到端 ZDR？
- [ ] 对外隐私说明是否与 OpenAI 的正式确认和实际架构一致？
