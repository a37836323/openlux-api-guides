# Gemini 3.5 Transcribe 接入指南：实时与录音转写 API 怎么选

**结论：**需要边说边出字、用于语音助手或实时字幕时，应评估 `gemini-3.5-transcribe-live` 与 Live API；处理会议录音、通话日志、质检或事后分析时，应评估 `gemini-3.5-transcribe` 与 Interactions API。若业务依赖说话人归属和词级时间戳，应优先选择预录音转写路径，并将稳定规划范围控制在不超过 3 名说话人。

本文适合准备在 Gemini API 中接入语音转写能力的开发者、产品负责人和技术选型人员。重点不是比较宣传指标，而是先按交互形态、输出要求和验证风险选择正确的 API 路径。

## 官方发布：模型、接口与当前状态

DeepMind 于 **2026 年 8 月 26 日**宣布 Gemini 3.5 Transcribe。官方说明，开发者可通过 Google AI Studio 中的 Gemini API 使用该模型，当前状态为**公开预览**。

官方将转写能力分为两条接口路径：

| 业务需求 | 官方 API | 模型 ID | 官方明确的输出或特性 | 适合的工作流 |
|---|---|---|---|---|
| 连续接收语音并持续返回转写结果 | Live API | `gemini-3.5-transcribe-live` | 双向流式转写；官方称延迟低于一秒 | 语音助手、实时字幕、交互式语音界面 |
| 上传或提交已录制音频后处理 | Interactions API | `gemini-3.5-transcribe` | 说话人归属、词级时间戳 | 会议纪要、通话记录、质检、事后检索与分析 |

两者都是 Gemini 3.5 Transcribe 的接入方式，但不能因为模型名称相近就把接口能力视为完全相同。尤其是说话人归属和词级时间戳，官方材料明确归在预录音处理场景，应以 Interactions API 路径验证。

## 先按交互方式选：实时流还是录音处理

选择的核心不是“音频长短”，而是应用是否必须在用户说话期间持续获得结果。

### 适合 Live API 的场景

如果用户会根据系统返回继续说话、修改表达或等待字幕更新，实时链路更匹配。典型包括：

- 语音输入型应用；
- 对话式语音助手；
- 在线会议实时字幕；
- 需要连续音频流与持续文本回传的交互界面。

官方为该路径给出的模型 ID 是 `gemini-3.5-transcribe-live`，并称其转写延迟低于一秒。产品设计时应把这理解为**模型侧的官方描述**，而不是端到端体验承诺：采集、网络传输、前端渲染、重连和业务后处理仍会影响用户看到文本的时间。

### 适合 Interactions API 的场景

如果音频已经录制完成，或业务必须先拿到完整录音再进行归档、审阅和分析，预录音路径更合适。其模型 ID 为 `gemini-3.5-transcribe`。

这一路径尤其适用于：

- 多人会议录音的整理；
- 客服通话日志；
- 访谈、培训或课程录音；
- 需要按词定位音频位置的审核系统；
- 基于说话人区分进行后续分析的流程。

不要为了获得实时感而把事后分析任务强行设计成流式系统。如果最终仍需完整录音、明确的说话人和可定位的词级时间信息，直接走预录音转写通常更贴近输出要求。

## 说话人归属与时间戳：把边界写进需求

**官方发布事实：**预录音转写支持说话人归属和词级时间戳；说话人归属最多支持 3 名说话人，超过 3 名属于实验性支持。

这意味着需求文档应避免只写“支持多人会议”。更可执行的写法是：

1. 业务是否必须区分发言人；
2. 是否要把文本精确定位到词级时间；
3. 常见录音中实际会出现几名说话人；
4. 超过 3 人时，产品如何呈现或回退；
5. 错误归属是否会触发人工复核。

**作者建议：**如果核心流程要求稳定地按人归档、统计或触发后续动作，应把“不超过 3 名说话人”作为当前可规划的范围。对于 3 人以上录音，不宜直接把实验性支持当作既定交付条件；应采用真实会议样本单独测试，并准备不展示归属、提示人工校对或拆分音频等回退方案。

同理，词级时间戳适合用于播放器跳转、证据定位、编辑器高亮等功能。若产品只展示整段文字，则没有必要在第一版就围绕词级信息设计复杂的数据结构。

## 自定义词汇与多语言：先建立业务词表

**官方发布事实：**Gemini 3.5 Transcribe 支持提供自定义词汇，并可自动检测和转写超过 85 种语言。

自定义词汇对于专有名词、产品名、药品名、缩写、代码、地名及特殊拼写尤其重要。但“支持”不等于无需验证。官方材料未在给定信息中说明具体请求字段、词表容量、格式或适用范围，因此接入时不应自行假定参数名称或结构。

**作者建议：**先维护一份与业务相关的最小词表，而不是一次性堆入大量术语。词表可按以下维度组织：

- 品牌、产品和内部项目名称；
- 人名、客户名及常见别名；
- 行业缩写与字母数字组合；
- 容易被误写的外文或特殊拼写；
- 不同语言中需要保留原样的术语。

随后，依据官方 API 文档提供的方式提交自定义词汇，并与“不提供词表”的基线结果对照。验证重点应是术语是否被正确识别、是否破坏周边语句，以及多语言切换时是否仍符合业务预期。

## 一个可执行的接入与验证流程

由于当前为公开预览，建议把“能调通”与“可进入生产流程”分成两个阶段。

### 阶段一：确定路径并完成最小接入

1. 明确输入是连续音频流还是已完成录音。
2. 实时需求选择 Live API，并使用 `gemini-3.5-transcribe-live`。
3. 录音处理需求选择 Interactions API，并使用 `gemini-3.5-transcribe`。
4. 从 Google AI Studio 的 Gemini API 文档确认认证、音频提交方式、请求格式和返回结构。
5. 不要依据模型名称猜测两个 API 的字段能够互换。

### 阶段二：用业务样本验证输出

准备经授权、可用于测试的音频集，至少覆盖：

- 单人清晰语音；
- 有背景声或停顿的语音；
- 含自定义词汇的内容；
- 目标语言及可能出现的语言切换；
- 两至三名说话人的录音；
- 若业务确有需要，单独加入 3 人以上录音作为实验性能力评估。

对预录音路径，检查说话人标签是否满足业务需要、词级时间信息能否支持前端定位。对实时路径，检查持续输出是否满足交互节奏，并记录从采集到页面显示的端到端时间，而非仅参考官方的模型延迟表述。

### 阶段三：制定上线门槛与回退

建议在上线前明确：

- 哪些语言、场景和词表版本在首期支持范围内；
- 说话人数量超过 3 人时的处理规则；
- 转写结果是否需要人工确认后才能进入高影响业务；
- 音频与文本的保存、访问和删除策略；
- 公开预览阶段出现接口变化时的版本管理与回归测试流程。

## 上线前检查清单

- [ ] 已根据实时或预录音需求选择 Live API 或 Interactions API  
- [ ] 已使用正确模型 ID，而非仅按名称匹配  
- [ ] 已确认预录音场景是否需要说话人归属与词级时间戳  
- [ ] 已将稳定的说话人归属范围限定为不超过 3 人  
- [ ] 已为 3 人以上音频设计实验测试或产品回退方式  
- [ ] 已建立并验证自定义词汇表  
- [ ] 已用目标语言和真实业务音频做测试  
- [ ] 已区分模型侧延迟描述与应用端到端体验  
- [ ] 已针对公开预览状态建立接口变更监测和回归测试  
- [ ] 已确认音频数据处理符合自身的隐私、合规与授权要求
